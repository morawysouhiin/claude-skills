# 責任分界点の設計

**入力**: 関係性(当事者、連携方式、データフロー)
**出力**: ①想定される障害事例の提案 ②定義すべき責任境界 ③責任分界表と全体図

## このスキルの立ち位置

障害が起きてから「どちらの責任か」を決めるのは遅い。揉めるのは、決めていなかったからである。したがってこのスキルは、**まだ何も起きていない関係性を入力として、起きうることを先回りして列挙し、決めておくべき事項の一覧に変換する**。

成果物は2つの場面で使われる:

- **自社の設計レビュー** — 抜け漏れの検出。したがって網羅性が最優先である
- **相手方との契約・仕様のたたき台** — したがって相手に渡せる書き方でなければならない

この2つ目の制約は重い。**責任を断定する書き方をしてはならない。** 「Bの責任である」ではなく「Bが担うか、Aが担うか、共同で担うかを定める。案1〜案3」と書く。まだ合意していないことを合意済みのように書けば、たたき台として使えなくなる。

## 不明点の扱い

**不明な点は必ず1つずつ聞く。** まとめて5問投げない。ユーザは連携の詳細を頭から順に思い出しながら答えるので、1問ずつのほうが精度の高い答えが返る。

質問して埋めるのは、**その答えによって出力が変わる項目だけ**にする。答えが分からなくても「未確認」として先へ進める項目は、質問せず未確認のまま記録する。質問の総数が多くなるときは、まず先に暫定版を作り、後から精度を上げるほうがよい。

## 手順

### ステップ1: 関係性の構造化

次を埋める。埋まらない項目は1つずつ質問するか、「未確認」と記録する。

- **当事者**: 組織名または役割名。保有者と運用者が異なる場合は分けて書く
- **システム/構成要素**: 各当事者が持つもの。中間に置かれる基盤(SFTP、MQ、API GW、共有ストレージ、VPN装置)は必ず独立した要素として扱う
- **連携方式**: ファイル転送/API/メッセージング/DB共有/手作業、同期か非同期か、起動契機(スケジュール、イベント、手動)
- **データフロー**: 何が、どちらからどちらへ、どの頻度で、どの経路を通って流れるか
- **業務上の意味**: そのデータが止まると、最終的に誰の何が困るか

最後の項目を飛ばさないこと。障害事例の影響度も、エンドユーザへの説明責任も、ここが起点になる。

### ステップ2: 引き渡し点の抽出と採番

**情報・データ・制御が、システムによって自動的に当事者の境界を越える地点**を列挙し、`H1`, `H2`... と採番する。この番号は以降すべての成果物で共通のキーになる。

中間基盤がある場合、**必ず2つの引き渡し点に分解する**(送信側→基盤、基盤→受信側)。1本の矢印にまとめると「送ったのに届いていない」という最頻出の事象を表現できなくなる。

**人手の連絡経路は引き渡し点として抽出しない。** メンテナンス予定の連絡、障害時の問い合わせ、エンドユーザへの説明などは、引き渡し点ではなく別の場所で扱う。理由は2つある。ひとつは、機械的な障害モード走査になじまず「該当なし」を量産して網羅性の証跡を薄めてしまうこと。もうひとつは、より重要で、**人手経路を引き渡し点として立てると「人が連絡すればよい」という解に逃げられてしまう**ことである。それは実務上必ず抜ける解であり、設計の失敗を先送りする。

人手経路に関わる論点は、次のようにデータ経路側へ割り当てる:

| 人手でやり取りされていること | 割り当て先 |
|---|---|
| 相手方の計画停止・臨時停止の予定 | 障害モード `M09 計画停止` |
| 仕様変更の事前連絡 | 障害モード `M11 仕様不整合` |
| 監視アラートの宛先・受け手 | 障害モード `M13 監視・通知の不達` |
| 異常検知時の当事者間の連絡 | 観点 `通知` |
| エンドユーザへの説明・問い合わせ対応 | 観点 `ユーザ説明` |

この割り当てにより、「Bが停止していることをどう知るか」は連絡の問題ではなく、**H2の設計上の問題**として扱われる。

### ステップ3: 障害事例の網羅列挙

`references/failure-modes.md` を読み、**引き渡し点 × 障害モード**の全組み合わせを機械的に走査する。優先度で絞らない。網羅が目的である。

各組み合わせについて `H1-M01` の形式でIDを振り、次を書く:

- **想定事象**: その引き渡し点で、その障害モードが起きると具体的に何が起きるか。関係性の具体名(システム名、ファイル名、経路)を使って書くこと。抽象的な記述は設計レビューで使えない
- **業務影響**: 最終的に誰が困るか
- **揉める点**: この事象が起きたとき、当事者間で何が争点になるか

**該当しない組み合わせは省略せず、「該当なし」と理由を書いて残す。** 消してしまうと、網羅したのか見落としたのかが後から分からなくなる。これは設計レビュー用成果物として致命的である。

### ステップ4: 定義すべき責任境界の導出

ステップ3の各事例から、決めておくべき事項を抽出する。同じ事項が複数の事例から出てくるので、**事項側にまとめて `D1`, `D2`... と採番し、関連する障害事例IDを紐づける**。

各事項は必ず次の5観点のいずれかに分類する:

| 観点 | 内容 |
|---|---|
| **完了定義** | 正常に終わったことを何をもって判断するか、誰が保証するか |
| **検知** | 異常を誰が、どの手段で、どれだけの時間で検知するか |
| **通知** | 検知した事実を誰に、どの手段で、いつまでに伝えるか |
| **ユーザ説明** | エンドユーザに誰が何を伝えるか |
| **復旧・費用** | 誰が復旧作業を行うか、再送・再処理の範囲、費用負担 |

そして各事項に、**決め方の選択肢を2つ以上**付ける。これが契約のたたき台としての中身になる。選択肢には、それぞれの実装コストと、その案を選んだ場合に残るリスクを併記する。

さらに **記載先の候補**(契約書/連携仕様書/運用手順書/監視設計書)を付ける。どの文書に落とすかまで書けば、そのまま次のアクションになる。

**粒度をそろえる。** 1つの事項が、**1つの取り決め(契約書なら条文1つ、仕様書なら節1つ)に落ちる大きさ**になるまで分割する。「異常時の連絡手段全般を定める」のような包括的な事項は、そのままでは条文にできない。次の基準で割る:

- 観点が2つ以上混ざっていたら割る(検知と通知は別の事項)
- 引き渡し点によって答えが変わるなら割る(H1の連絡先とH4の連絡先が別なら別の事項)
- 案1と案2が同じ土俵で比較できないなら、事項が大きすぎる兆候である

逆に、複数の引き渡し点で答えが完全に同じになる事項は1つにまとめ、`対象引き渡し点` に複数書く。

### ステップ5: 是正・設計上の原則

選択肢を提示する際、次の原則を守る:

- **人手による随時連絡だけに依存する案を単独で提示しない。** 「メンテナンス予定を都度メールで連絡する」類は実務上必ず抜ける。運用案を出す場合は、抜けたときに機械側で検知できる手段を必ずセットにする
- **「送信完了」と「受領完了」を常に別事象として扱う**
- **エンドユーザが最初の検知者になる構成は、検知設計が存在しないことと同義**として扱い、明示的に指摘する

### ステップ6: 成果物の生成

`references/output-spec.md` に表の列定義とファイル構成を定めてある。**必ず読んでから生成すること。**

生成物は4点:

| ファイル | 内容 |
|---|---|
| `responsibility-boundary.puml` | 全体図(構成 + 引き渡し点番号) |
| `failure-cases.csv` | 表A: 想定障害事例一覧 |
| `boundary-definitions.csv` | 表B: 定義すべき責任境界一覧 |
| `responsibility-boundary.html` | 全体図(SVG埋め込み) + 表A + 表B + 前提と未確認事項 |

図の記法は `references/diagram-conventions.md` を参照。**図はシーケンス図ではなく構成図**である。障害の時系列は図に描かない。図の役割は「関係性の全体像と引き渡し点の位置を1枚で示す」ことだけに限定する。

SVGへの変換:

```bash
bash scripts/render_puml.sh <input.puml> <output.svg>
```

初回のみ PlantUML の jar を取得してキャッシュする。ネットワークが使えない場合は SVG 埋め込みを諦め、HTMLに .puml のソースを載せて外部レンダラでの表示を案内する。

CSVは Excel で開かれるので **UTF-8 BOM付き** で書き出す。

## 出力例(表Bの1行)

```
D3 | H1, H2 | 完了定義
決めるべき事項: 送信側が「送信完了」と判断する条件に、受信側の受領を含めるかどうか
関連事例: H1-M01, H1-M09, H2-M01, H2-M08
案1: 受信側が取込完了時に完了通知ファイルを返し、送信側は一定時間内に得られなければ未達として扱う
     (実装コスト: 中 / 残るリスク: 完了通知そのものの不達を別途検知する必要がある)
案2: 送信側は送信のみで完了とし、日次の件数突合で不一致を検出する
     (実装コスト: 小 / 残るリスク: 検知が最大1日遅れる)
記載先: 連携仕様書、監視設計書
```

責任者を断定せず、選択肢とトレードオフで書けている状態が正しい。
