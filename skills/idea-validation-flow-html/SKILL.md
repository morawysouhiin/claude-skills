# アイディア初期検証フロー（HTMLレポート出力）

新規開発の起点（アイディア または 困りごと）を受け取り、「その困りごとが実際にあるか」「そのアイディアが既に市場で実現していないか」を検証し、ブラッシュアップされた課題・ソリューションと次アクションを**単一のHTMLレポート**として出力するスキル。

このスキルの本質は、**「実在性の検証」と「既存解の検証」を独立した2軸として回し、その掛け合わせで意思決定する**こと。片方だけでは判断を誤る。

もう一つの柱は、**ワークシートに圧縮されて失われがちな裏側の分析詳細（根拠・数値・出典・却下した選択肢）を、レポートの折りたたみとして全て保存する**こと。結論だけが残り、なぜそう判断したかが消えた検証は、後から見直すことも他人に説明することもできない。

## いつ使うか / 使わないか

- **使う**: アイディア段階、困りごと段階、「需要あるか」「もうやられてないか」「筋がいいか」を知りたい段階。
- **使わない**: 既に課題も既存解も検証済みで、プロトタイピング・事業計画・資金調達など後段に入っている場合。その場合はこのスキルではなく該当フェーズの支援に移る。

## 想定用途（出力設計の前提）

生成物は次の2つを同時に満たす必要がある。どちらか一方に寄せない。

1. **自分用の検討ログ** — 網羅性が最優先。セッション中に検討した事実・数値・出典・却下した仮説を一つも落とさない。
2. **上司・出資者・関係者への共有資料** — 初見の第三者が、上から読んで判定と根拠を追える体裁であること。

この2つは「本文＝ワークシート（読みやすさ）／各欄直下の折りたたみ＝分析詳細（網羅性）」という構造で両立させる。

## 全体フロー

```
起点（アイディア or 困りごと）
   │
STEP 0  課題の言語化（アイディアは課題へ逆算 / 複数needは分割）
   │
STEP 1  実在性の検証   ── 一次・二次調査／需要の大きさ
   │
STEP 2  既存解の検証   ── 先行製品・特許・代替手段（要求バーに対して判定）
   │
判定ゲート  needの大きさ × 既存解のギャップ（+ feasibility 軽チェック）
   ├─ 中止        （需要が小さい / 既存解で充足）
   ├─ ピボット     （↻ STEP 0 へ課題を再定義）
   ├─ 条件付き前進  （成立すべき条件を明示 → STEP 3）
   └─ 前進        （検証済みの機会 → STEP 3）
                │
        STEP 3  ブラッシュアップ（支配的パラメータ＝最大リスク仮説の特定）
                │
        HTML生成（本スキル固有の最終工程）
```

線形ではなく反復ループ。ピボットも前進も STEP 0〜2 をもう一周する前提で運用すること。

## 分析ログの保持（本スキル固有の最重要ルール）

**フローを回している最中から、HTML化を前提に「捨てない」運用をすること。** 通常のワークシートは各欄1〜2行に圧縮されるため、そこに至る過程が消える。本スキルではその過程こそが折りたたみの中身になる。

STEP 0〜3 の各所で、以下が発生したら**その都度、どのワークシート欄に紐づくかを意識して保持する**:

- 参照した具体的な数値（有病率、市場規模、価格、件数、頻度など）とその出典
- 参照した文献・特許・製品名・URL・データベース
- 検討したが**採用しなかった**選択肢と、却下した理由
- 判定に至る推論の筋道（「Aだから、Bと仮定すると、Cになる」）
- ユーザーの発言のうち、判定の根拠になった原文
- 前提として置いた数字が実測なのか仮置きなのか

**これらを最後にまとめて思い出そうとしないこと。** 情報の欠落はここで起きる。各STEPを終えるたびに、その時点で保持すべき詳細を頭の中で確定させてから次へ進む。

## 不明事実ログ（全STEPを横断する仕組み）

STEP 0〜2・判定ゲートの各所で、「本当はまだ確認していないのに、暗黙のうちに前提として使ってしまっている事実」が必ず生まれる。これをその場その場で「未検証」と書いて済ませるのではなく、**一つのログに集約し、事実ごとに調査タイプを仕分けて、具体的な調査アクションに変換する。**

このログは STEP 0 の直後から作り始め、STEP 1・STEP 2 を通じて随時追記し、判定ゲートに入る前に一度棚卸しする。

各項目には、次の4つを必ず記録する:

1. **不明確な事実/前提**: 何が確認できていないか
2. **関連STEP**: STEP0（need statement）／STEP1（実在性）／STEP2（既存解）／判定ゲート（支配的パラメータ・feasibility）のどれに紐づくか
3. **調査タイプ**（必ずいずれかに仕分ける。曖昧なまま残さない）:
   - **定量調査**: 疫学データ、有病率、市場規模、価格データ、特許件数、頻度・回避コストの実測値など、数値・データで決着する事実。二次資料のデータベース検索、統計、あるいは簡易なモデル化（例: マイクロシミュレーション、感度分析）で埋める。
   - **定性調査**: 当事者インタビュー、行動観察、専門家ヒアリング、DIY workaroundの実態など、数値化しにくいが当事者の実際の行動・言葉で決着する事実。The Mom Test の原則（将来の意向でなく過去の実際の行動を聞く）に従う。
   - **机上調査**: 学術文献・特許明細書・規制/償還制度の条文など、既に存在する公開情報の読解で決着する事実。
4. **具体的な調査アクション**: 「何を」「どこで」「誰に」調べるかを一文で書く。「調べる」で終わらせない。

**このログの目的は網羅ではなく優先順位付け。** 判定ゲートの支配的パラメータは、多くの場合このログの最優先項目と一致するはずである。一致しない場合はどちらかを疑う。

HTML では各行に、その不明事実がなぜ不明なのか（どこまで調べて、どこで詰まったか）を折りたたみで添えること。

## 実行手順

### STEP 0 — 課題の言語化

**まず起点が「アイディア」か「困りごと」かを判別する。** ここを飛ばすと後段が崩れる。

- 起点が「困りごと」なら、そのまま need statement（誰が・どんな状況で・何に困っているか）に整形する。
- 起点が「アイディア」なら、**アイディアは検証できないという前提に立つ**。検証できるのは課題（need）だけ。「このアイディアが解こうとしている課題は何か」を逆算し、need statement に変換する。

理由: solution先行のまま進むと「デバイスの良し悪し」を検証してしまい、「そのニーズが実在するか」が空白のまま進む。

**Example:**
Input（アイディア）: 家庭用の指先クレアチニン測定器がほしい
Output（課題）: すでに診断済みのCKD高リスク患者が、eGFRの悪化トレンドを来院間隔より細かく把握できていない

**アイディアが複数の need を束ねていないか確認する。** 束ねている場合は分割し、**各 need を別々にこのフローへ通す**。押し込むと濁った結論になり、鋭い分岐を失う。

→ 保持すべき詳細: 逆算の推論過程、検討した別解釈の need statement とその却下理由、分割判断の根拠。

### STEP 1 — 実在性の検証（needが本当にあるか）

2系統を**独立に**回す。片方だけで結論を出さない。

- **二次調査（desk）**: 疫学データ、市場レポート、学術文献、レビュー／フォーラムの生の不満、既存製品の口コミ。
- **一次調査（primary）**: 当事者インタビュー、可能なら行動観察。

**「存在するか」と「解く価値があるほど大きいか」を必ず分ける。**

> 需要の大きさ = 頻度 × 深刻度 × 現状の回避コスト

回避コストがゼロに近い課題は、実在しても優先度は低い。

**インタビューの最大の罠は誘導。** 将来の意向でなく過去の実際の行動を聞く（The Mom Test）。

**根拠が弱い（推測・伝聞・単一情報源のみ）事実は判定に使わず不明事実ログへ転記する。** 特に頻度・深刻度・回避コストの3変数のうち仮置きの数字は必ずログに載せる。

→ 保持すべき詳細: 参照した統計・文献の具体的数値と出典、3変数それぞれの推定根拠と実測/仮置きの別、口コミ・フォーラムの具体的な記述内容。

### STEP 2 — 既存解の検証（すでに市場で実現していないか）

以下を網羅的に見る:
- 先行製品・競合
- 特許（prior art / FTO）
- 学術プロトタイプ
- 隣接領域の解
- **ユーザーが自作している回避策（DIY workaround）** ← 見落としやすいが最重要級のシグナル

結果を3分類する。**判定は「存在の有無」でなく、自分の価値提案が要求するエビデンス/品質バーに対して**行う。どの水準に対する判定かを必ず添える。
- **十分に解かれている**（そのバーで） → 撤退か、明確な楔（wedge）を探す
- **部分的に解かれている** → 差別化の余地あり
- **解かれていない**（そのバーで） → 下記の注意を必ず適用する

**「誰もやっていない」は両義的なシグナル。** 理由が次のどれかを特定する:
- (a) 技術・規制が難しい（医療機器では規制/償還がボトルネックのことが多い）
- (b) 需要が小さい
- (c) 本当に見落とされている（=真の機会）

(a)(b) と (c) を取り違えないことが、この STEP の全て。

**分類判定や(a)(b)(c)の切り分けが推測に基づく場合は必ず不明事実ログへ転記する。**

→ 保持すべき詳細: 調べた製品名・企業名・特許番号・文献の一覧（判定に効かなかったものも含めて全て）、検索に使ったキーワードと検索先、各競合をどのバーで評価したか。

#### 特許調査の必須化と判定格下げルール（強制）

特許調査は STEP 2 の中で最も飛ばされやすく、かつ飛ばしたことが判定に反映されないまま前進してしまう。これを構造的に防ぐため、以下を**例外なく**適用する。

**「実施した」と認める条件（3軸すべてを満たすこと）**

1. **コア機能軸**: need のコア機能そのものを表す語で検索した
2. **原理軸**: 想定するソリューションの検出/測定/作用原理を表す語で検索した
3. **出願人軸**: STEP 2 で見つけた既存製品・競合の出願人名で検索した

かつ、次を**記録**していること。記録がなければ実施とみなさない。

- 使用した検索先（例: J-PlatPat、Espacenet、Google Patents など複数）
- 実際の検索式・キーワード
- ヒットの有無と、関連しうる代表的な文献番号（ゼロ件ならゼロ件と明記）

**「検索しようと思った」「一般に特許は多いはず」は実施ではない。3軸のうち1つでも欠けていれば部分実施＝未実施として扱う。**

**未実施だった場合に強制される格下げ**

- **判定「前進」を出すことを禁止する。** 上限は「条件付き前進」。すでに「前進」と書きかけていたら書き直す。
- **成立条件の第1項を「特許調査（prior art / FTO）の実施」で固定する。** 他の条件より上に置く。
- **kill criteria に特許関連の条件を必ず1つ追加する。** 例: 「コア機能をカバーする有効な先行特許が存在しないこと、または回避設計が可能であること」。
- **不明事実ログに、未実施であることを最優先級の項目として立てる。** 調査アクションには上記3軸を具体的に書く。

**後追いの自己申告では代替できない。** フッターや「網羅性の限界」に「特許調査は未実施です」と書くだけでは、この要件を満たさない。**判定そのものを格下げすること**が要件である。限界の記載は、格下げに加えて行う。

**HTML への反映義務**

- 判定サマリーバナーの中に、特許調査の実施状況バッジ（`特許調査: 実施済` / `特許調査: 未実施`）を**必ず表示する**。フッターだけに書くのは違反。
- 未実施の場合、判定値の直下に「特許調査未実施のため上限判定」という趣旨の一文を添える。

**なぜここまで強制するか。** 既存製品が市場に存在する領域では、周辺特許が押さえられている確率が高い。特許を見ずに出した「前進」は、参入可能性を確認しないまま前進と言っているに等しく、後段の投資判断を誤らせる。需要や既存解の評価が正しくても、この一点で事業が成立しなくなりうる。

### 判定ゲート — needの大きさ × 既存解のギャップ

|              | 既存解のギャップ大 | 既存解のギャップ小 |
|--------------|:---:|:---:|
| **需要大** | 前進 | 条件付き前進 or 楔探し |
| **需要小** | ピボット | 中止 |

**判定を clean な go/kill に無理に押し込めない。** 初期検証の結論は「◯◯が成立すれば費用対効果的／勝てる」という**条件付き前進**になることが多い。成立すべき条件を箇条書きで明示し、STEP 3 に渡す。

**判定を最も左右する単一パラメータ（dominant sensitivity parameter）を1つ特定する。** それを最大リスク仮説として STEP 3 に引き継ぐ。

**あわせて feasibility を軽く確認する。** 中核メカニズムに未証明の科学的前提がある場合、それ自体が支配的パラメータになりやすい。詳細な技術フィジビリティは別プロセスに委ねる。

**合否基準（kill criteria）は検証を始める前に数値で宣言しておくこと。** 単一閾値でも、複数条件のAND でもよい。医療機器の費用対効果のように複数の enrichment 条件が同時に揃って初めて成立するケースでは AND条件として明示的に書く。

**判定ゲートに入る前に不明事実ログを一度棚卸しする。** 支配的パラメータや kill criteria の閾値そのものが不明事実ログの項目と重なっている場合、その調査が完了するまでは「前進」ではなく「条件付き前進」までしか判定できない。

**あわせて、判定を確定する前に STEP 2 の特許調査の実施状況を必ず確認する。** 未実施であれば、他の材料がどれだけ揃っていても「前進」は出せない（上限は「条件付き前進」）。この確認を飛ばさないこと。

→ 保持すべき詳細: 支配的パラメータを選んだ理由と、対抗馬として検討した他のパラメータ、kill criteria の閾値の設定根拠、判定が反転する条件。

### STEP 3 — ブラッシュアップ（前進 / 条件付き前進時）

1. 学びを反映して need statement を再定義する
2. 最初のアイディア1個に固定せず、複数のソリューション案を出す
3. 具体的な value proposition とターゲットセグメントを定義する
4. **支配的パラメータを最大リスク仮説として引き継ぎ**、それを潰す検証を次サイクルに渡す

STEP 3 の出口は「完成した答え」ではなく「次に潰すべき最大の不確実性」。

→ 保持すべき詳細: 出したソリューション案のうち採用しなかったものと却下理由。

## HTML生成（本スキル固有の最終工程）

STEP 3 まで終えたら、**単一のHTMLファイル**を生成し、実行環境の出力先（作業ディレクトリ、または環境が指定する成果物フォルダ）に保存して、ユーザーがダウンロード・閲覧できる形で提示する。

### 技術要件

- **単一ファイル完結**。CSS・JavaScript は全てインラインで埋め込む。外部CDN・外部フォント・外部画像への依存は禁止（オフラインでも、メール添付でも開けること）。
- 言語は日本語。`<html lang="ja">`、`<meta charset="utf-8">`、`<meta name="viewport" content="width=device-width, initial-scale=1">` を必ず付ける。
- フォントは system font stack（`system-ui, -apple-system, "Hiragino Sans", "Noto Sans JP", Meiryo, sans-serif`）。
- ファイル名は `idea-validation_<テーマの短いスラッグ>_<YYYYMMDD>.html`。
- 印刷対応: `window.onbeforeprint` で全ての `<details>` を `open` にする。折りたたんだままだと印刷・PDF化で中身が消えるため、これは必須。

### 構造

上から順に:

1. **ヘッダー** — テーマ名、生成日、起点の種別（アイディア/困りごと）
2. **判定サマリーバナー** — 判定（中止/ピボット/条件付き前進/前進）を大きく色分けして表示。あわせて need statement、支配的パラメータ、次アクションの3点を1画面で読めるようにする。読み手が最初に見る領域。
   - 中止=赤系、ピボット=橙系、条件付き前進=黄系、前進=緑系
   - **特許調査の実施状況バッジを必ずこのバナー内に置く**（`特許調査: 実施済` / `特許調査: 未実施`）。未実施の場合は判定値の直下に「特許調査未実施のため上限判定」と添える。省略不可。
3. **目次** — 各セクションへのアンカーリンク。長くなるので `position: sticky` で追従させてよい。
4. **全展開／全折りたたみボタン** — ページ上部に配置。共有相手が中身を一括で開けるようにする。
5. **本体セクション** — STEP 0 → STEP 1 → STEP 2 → 不明事実ログ → 判定ゲート → STEP 3 → 次アクション
6. **フッター** — このスキルの限界（下記「正直に伝えるべき限界」の要旨）を明記

### 折りたたみの作り方（本スキルの核心）

ワークシートの**各欄ごとに**、本文（1〜2行の結論）の直下に `<details>` を1つ置く。

```html
<div class="field">
  <div class="field-label">需要の大きさ（頻度 × 深刻度 × 回避コスト）</div>
  <div class="field-value">結論を1〜2行で</div>
  <details>
    <summary>分析詳細（根拠・数値・出典）</summary>
    <div class="detail-body">
      <!-- 参照した数値と出典、推論の筋道、却下した選択肢、実測/仮置きの別 -->
    </div>
  </details>
</div>
```

**折りたたみの中身が空になる欄があってはならない。** 詳細が本当に無い場合は「この欄は◯◯という理由で追加の分析を行っていない」と明記する。空の `<details>` を置くくらいなら、なぜ無いかを書く。

詳細の中では、次を明示的にラベル付けして書き分けること:
- **根拠**: 判定を支えた事実
- **数値と出典**: 数値は必ず出典とセットで。出典が無い数値は「出典なし・仮置き」と明記
- **推論**: 事実から結論に至る筋道
- **却下した選択肢**: 検討したが採らなかった案と理由
- **ユーザー発言**: 判定の根拠になった原文（引用として）

### 状態の視覚化

- **未検証**: `未検証` バッジを目立つ色（灰地に赤文字等）で表示。空欄で済ませない。
- **仮置きの数値**: 数値の直後に `仮置き` バッジ。実測値と視覚的に区別できること。
- **不明事実ログ**: 表形式。調査タイプ（定量/定性/机上）を色分けバッジに、優先度（高/中/低）も色分け。各行の末尾に折りたたみで「どこまで調べて詰まったか」を入れる。
- **判定ゲート**: 2×2マトリクスをHTMLの表で描画し、該当セルをハイライトする。

### 情報欠落の防止（生成前セルフチェック）

HTMLを書き出す前に、以下を全て確認する。1つでも該当したら書き出さない。

- [ ] セッション中に言及した数値・出典・製品名・特許番号が、本文か折りたたみのどこかに全て載っているか
- [ ] 検討したが却下した選択肢（need statement案、ソリューション案、支配的パラメータの対抗馬）が全て記録されているか
- [ ] 空の `<details>` が1つも無いか
- [ ] 「未検証」の欄が空欄でなく、バッジ付きで明示されているか
- [ ] 不明事実ログの全行に、調査タイプ・具体的調査アクション・優先度が入っているか
- [ ] 特許調査を3軸（コア機能・原理・出願人）すべてで実施し、検索先・検索式・ヒットの有無を記録したか
- [ ] 特許調査が未実施なら、判定が「条件付き前進」以下に格下げされ、成立条件の第1項が特許調査になっており、kill criteria に特許条件が入っており、判定サマリーバナーに `特許調査: 未実施` バッジが出ているか
- [ ] 支配的パラメータが1つだけ特定され、不明事実ログの最優先項目と突き合わせ済みか
- [ ] kill criteria が検証**前**に宣言したものとして書かれているか（後付けになっていないか）
- [ ] 外部リソースへの参照（CDN、外部フォント、外部画像）が1つも無いか
- [ ] `window.onbeforeprint` で全 `<details>` を開く処理が入っているか

**要約したくなったら、それは欠落のサイン。** 本文を短くするのは構わないが、その分は必ず折りたたみに移す。捨てるのではなく移す。

### 出力後にユーザーへ伝えること

HTMLを提示したら、次を短く添える:
- 折りたたみを開くと分析詳細が読めること
- 一次調査（インタビュー）は未実施であること（実施していない場合）
- 支配的パラメータと、次に潰すべき不確実性

## よくある失敗（ガードレール）

実行中に自分自身をチェックする項目。該当したら立ち止まる。

- **アイディアをそのまま検証しようとする** → STEP 0 で課題へ逆算し直す。
- **複数needを1つのneed statementに押し込む** → 分割して各々をフローに通す。
- **「存在」と「大きさ」を混同する** → 存在しても回避コストが小さければ需要は小さい。
- **既存解を「存在の有無」だけで判定する** → 自分の要求バーに対して判定する。
- **インタビューで将来の意向を聞く** → 過去の行動を聞く。
- **「誰もやっていない=チャンス」と即断する** → 理由(a)(b)(c)を切り分ける。
- **特許調査を飛ばしたまま判定に進む** → 3軸の実施と記録がなければ「前進」は出せない。上限は「条件付き前進」。
- **特許調査の未実施を「網羅性の限界」に書いて済ませる** → 記載は必要だが、それだけでは不足。判定そのものを格下げすること。
- **検証後に合否基準を後付けする** → kill criteria は必ず着手前に宣言する。
- **clean な go/kill に無理に押し込める** → 成立条件を明示した条件付き前進を使う。
- **どの1変数が結論を律するか特定しない** → 判定ゲートで支配的パラメータを必ず1つ挙げる。
- **不明な事実を憶測で埋める** → 不明事実ログに追加して調査アクションに変換する。
- **HTML化の際に「見やすさのため」情報を削る** → 削らずに折りたたみへ移す。これが本スキル最大の失敗モード。
- **折りたたみを空のまま置く** → なぜ詳細が無いのかを書く。
- **セッション後半でSTEP 0〜1の詳細を思い出せず省略する** → 各STEP終了時点で保持内容を確定させておく。
- **外部CDNやフォントを読み込む** → 単一ファイル完結を破ると共有先で崩れる。

## 正直に伝えるべき限界

このスキルは**構造**であって、実在性や既存解の中身（テーマ固有の市場・特許状況）は個別調査でしか埋まらない。フローを回すこと自体が答えを出すわけではない点を、ユーザーに誤解させないこと。

**HTML化についても同様。** 体裁が整うことと検証が進むことは別である。見栄えの良いHTMLは、根拠の薄さを見えにくくする副作用があるため、「未検証」「仮置き」のバッジは必ず目立たせること。

**不明事実ログについて。** 定性調査（当事者インタビュー・行動観察）はユーザー自身が実施しない限り実データは得られない。定量調査・机上調査（統計検索、特許検索、文献レビュー、簡易モデル計算）は積極的に代行してよいが、一次インタビューの実施を代行できるわけではない点を明確に伝えること。
